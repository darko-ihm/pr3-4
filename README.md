## Вимоги
- Python 3.10+
- `pip install -r requirements.txt`

## Швидкий старт
```bash
# 1) Симетрія: створити ключ і зашифрувати/розшифрувати файл (GCM)
python cli.py sym new --label default
python cli.py sym enc --label default --in data/sample.txt --out outputs/sample.gcm --mode gcm
python cli.py sym dec --label default --in outputs/sample.gcm --out outputs/sample.dec

# 2) RSA: згенерувати ключі, підписати та перевірити
python cli.py rsa gen --priv keys/priv.pem --pub keys/pub.pem --password changeit --bits 3072
python cli.py rsa sign --priv keys/priv.pem --password changeit --in data/sample.txt --sig outputs/sample.sig
python cli.py rsa verify --pub keys/pub.pem --in data/sample.txt --sig outputs/sample.sig

# 3) Гібрид: шифрувати AES‑ключ RSA‑OAEP + дані AES‑GCM
python cli.py hybrid enc --pub keys/pub.pem --in data/sample.txt --out outputs/sample.hybr
python cli.py hybrid dec --priv keys/priv.pem --password changeit --in outputs/sample.hybr --out outputs/sample.hybr.dec

# 4) Бенчмарки
python cli.py bench --sizes 1MB 10MB --modes gcm cbc --rsa-bits 2048 3072 4096
```

## Аргументовані висновки щодо оптимальності алгоритмів та результати аудиту:

1. **Аналіз продуктивності симетричного шифрування:** 
   Результати бенчмарків підтверджують, що режим AES-GCM демонструє вищу швидкість як при шифруванні, так і при дешифруванні порівняно з AES-CBC. Це пов'язано з тим, що GCM поєднує шифрування та обчислення тегу аутентифікації на апаратному рівні, тоді як CBC потребує окремої генерації та перевірки HMAC-SHA256, що додає обчислювальних накладних витрат. Тому для реальних проєктів (передача потокових даних, збереження файлів) доцільно використовувати саме GCM.

2. **Оцінка асиметричного шифрування (RSA):**
   Бенчмарки генерації ключів показують експоненційне зростання часу створення ключа при збільшенні його розміру з 2048 до 4096 біт. Використання ключів довжиною 3072 біти є оптимальним балансом, оскільки забезпечує достатній рівень безпеки за сучасними стандартами NIST без критичної втрати продуктивності.

3. **Гібридне шифрування як оптимальний підхід:**
   Оскільки RSA не призначений для шифрування великих масивів даних (через низьку швидкість та обмеження на розмір блоку), реалізована гібридна схема є найефективнішою. Одноразовий сеансовий ключ AES (256 біт) генерується миттєво, шифрує основний масив даних, після чого сам надійно упаковується за допомогою повільного, але безпечного RSA-OAEP.

4. **Аудит безпеки та виправлення вразливостей коду:**
   Під час тестування базового шаблону було виявлено та усунуто дві критичні архітектурні помилки:
   * **Проблема з ключем HMAC:** У режимі CBC для генерації підпису HMAC щоразу використовувався новий випадковий ключ, який не зберігався, а дешифрування відбувалося ключем із нулів (`b'\x00'*32`), що гарантовано призводило до помилки `InvalidSignature`. Проблему вирішено шляхом використання основного сеансового ключа для операцій HMAC.
   * **Пошкодження бінарної структури:** Вектор ініціалізації (IV) дублювався — він записувався і як метадані в JSON-заголовок, і як сирі байти безпосередньо у файл. Це спричиняло зсув даних при дешифруванні.

5. **Журналювання та безпека:**
   Реалізовано систему логування у форматі JSON (`logs/crypto.jsonl`), яка фіксує всі події без компрометації самих ключів. Також забезпечено належну обробку виняткових ситуацій (спроби підміни зашифрованого файлу перехоплюються валідацією HMAC у CBC та тегом аутентифікації у GCM).
   
6. Управління ключами та їх ротація: Симетричні ключі (256 біт) генеруються криптостійким модулем secrets. Для кожного нового сеансу шифрування автоматично генерується унікальний вектор ініціалізації (IV) або Nonce, що виконує роль криптографічної солі та унеможливлює злом через аналіз однакових шифротекстів. Для запобігання компрометації (ротація ключів), гібридний модуль автоматично створює новий унікальний сеансовий AES-ключ для кожного нового файлу.
